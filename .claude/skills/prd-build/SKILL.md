# PRD 이후 만들기 절차 (prd-build)

PRD 한 장을 실제로 쓰는 웹앱으로 만들어 배포할 때까지의 순서다. 한 바퀴: **PRD → GitHub Issue → Issue마다 개발(새 세션 하나 = Issue 하나 = PR 하나) → PR 검토·병합 → Issue 닫힘 → 다음 Issue → 배포 확인.** 결과물은 개인 = `tools/m5_*.html` 하나로 된 웹앱, 팀 = `tools/` 아래 여러 페이지 웹앱이고, 병합된 main은 GitHub Pages로 배포된다.

## 1. 언제 쓰나

| 호출 | 하는 일 |
|---|---|
| `/prd-build plan` | PRD를 점검하고([가정] 보충) Issue 초안·표본·계획(팀은 설계 메모·데이터 약속)으로 나눈다 |
| `/prd-build start #n` | Issue 하나의 구현 순서와 사람이 화면에서 볼 것을 먼저 보여 준다 |
| `/prd-build step` | 다음 작은 단위를 구현 → 확인 → diff 확인 → 커밋·푸시하고, 사람이 화면에서 볼 것을 알려 준다 |
| `/prd-build review` | 배포 확인·자체 검토를 쓴다(개인 `checks/m5_check.md`, 팀은 PR 본문 검토 절) |
| `/prd-build ship` | 병합 전 PR 본문 초안과 사람이 할 일 목록을 만든다 |

## 2. 먼저 읽는 것과 모드

- 매번 먼저 읽는다: `CLAUDE.md`, PRD, 계획 파일(있으면), `docs/design.md`(팀, 있으면)
- **개인 모드:** `prd/m5_my_prd.md`가 있으면. 계획 = `docs/m5_plan.md`, Issue 초안 = `docs/issues_draft/m5_{번호}.md`, 확인 = `checks/m5_check.md`, 웹앱 = `tools/m5_*.html` 하나, 커밋 머리 `[M5]`
- **팀 모드:** `prd/team_prd.md`가 있으면. 계획 = `docs/team_plan.md` + `docs/design.md` + `docs/issues_draft/1~4.md`, 커밋 머리 `[팀-{역할}]`(통합·기능A·기능B·검증데이터) 또는 `[팀]`
- 둘 다 있거나 둘 다 없으면 어느 모드인지 사용자에게 한 번 묻는다.
- 세션은 GitHub Issue를 볼 수 없다. Issue 본문이 필요하면 사용자에게 웹에서 복사해 붙여 넣어 달라고 한다.

## 3. 공통 규칙 (모든 호출)

1. 기존 파일과 사용자 변경을 덮어쓰지 않는다. `inputs/`와 `data/`의 원본 표본은 읽기만 한다.
2. 한 세션은 Issue 하나만 다룬다. 그 Issue의 완료 기준 밖 기능, 무관한 정리를 하지 않는다. 결과에 영향이 작은 선택은 이유 한 줄을 남기고 정한다.
3. 커밋·푸시는 묻지 않고 한다. **PR과 Issue는 초안 글만 쓴다** — 만들기·등록·리뷰 요청 전환·승인·병합은 사람이 한다(이 세션에서는 `gh pr`·`gh issue`가 동작하지 않는다).
4. main에 직접 푸시하지 않는다. 지금 세션 브랜치에만 푸시한다.
5. 웹앱은 서버 없이 파일을 더블클릭해 열었을 때도, Pages 주소로 열었을 때도 동작해야 한다. 외부 주소(http·https)·외부 라이브러리·fetch·`type="module"` 스크립트 파일을 쓰지 않는다. 개인은 스타일·스크립트를 HTML 파일 하나 안에, 팀은 공통 파일을 일반 script src로 부른다.
6. 화면 확인은 사람이 한다. 세션은 할 수 있는 확인(코드 읽기, 문법 확인, 함수 시험, 팀은 `python tests/run_acceptance.py`)만 하고, 사람이 화면에서 볼 것을 1~3줄로 알려 준다. 실행하지 않은 확인은 "미실행"이라고 쓴다. 확인을 지우거나 기준을 낮춰서 통과시키지 않는다.
7. 개인정보·실제 업무 자료·외부 전송을 넣지 않는다. 데이터는 가상 표본만 쓴다. 배포 주소는 누구나 열 수 있다.
8. 법규 적합·안전 판정·보상·계약금액·당첨·자격은 확정하지 않는다. 화면에 "담당 검토 후 확정"으로 보이게 한다.
9. 기대 결과는 사람이 표본을 보고 적는다. 기대 결과 칸은 비워 두고, 사람이 불러 준 문장만 적는다.
10. 보고는 실제로 확인한 것만 한다: 바꾼 파일, 확인 결과, 커밋 메시지, 사람이 화면에서 볼 것, 다음 할 일.

## 4. 호출별 절차

### plan — PRD 점검 → Issue 초안·표본

1. PRD를 점검한다: 결과물 형태(개인 = HTML 파일 하나, 팀 = 시작 페이지 + 기능 페이지 2개 + 공통 파일, 둘 다 Pages 배포), MVP 1개와 '다음', 화면(페이지) 이름, 입력 방법, 저장(localStorage 키 하나 + JSON 백업), 성공 시나리오 S1~S3(팀 S1~S4, '넣는 것 → 화면에 보일 것'). 빠졌거나 맞지 않는 것은 **[가정]**으로 채우고 바꾼 것을 표로 보여 준다.
2. 개인 모드:
   - `docs/issues_draft/m5_1.md~m5_3.md` — Issue 2~3개(1번 화면 틀과 표본 넣기, 2번 MVP 판정, 3번 저장·오류 안내·다듬기). 칸: 제목 · 목적 · 완료 기준(S 번호와 사람이 화면에서 볼 것) · 범위 밖 · 선행 Issue.
   - `docs/m5_plan.md` 양식 칸 — 1절 Issue 목록(웹 번호 칸은 비움), 2절 성공 시나리오, 3절 표본·경계값·함정 위치(기대 결과 칸은 비움).
   - `data/m5_sample.{csv | txt | json}` — 화면 입력에 맞게, 가상 10~20건, 경계값 1개 이상, 함정 1개.
   - `CLAUDE.md`에 '## 5. M5 개발 규칙' 절이 없으면 실습 안내 2절의 규칙 다섯 줄로 추가한다.
3. 팀 모드:
   - `docs/design.md` 양식 칸 — 1절 페이지 지도와 파일 경계, 2절 데이터 약속(키 `team{조}_app`, JSON 모양·예시 1건·쓰고 읽는 페이지), 3절 공통 함수 다섯 개, 4절 여는 방법.
   - `docs/team_plan.md` — 요구사항 R1~R3을 S 번호와 잇고, Issue 4개(① 뼈대·통합 ② 기능 A 페이지 ③ 기능 B 페이지 ④ 표본·수용 기준·파일 검사), 병합 순서 ① 뼈대·④ → ② → ③ → ① 통합, 대응표.
   - `docs/issues_draft/1.md~4.md`(작업 이슈 양식 칸), `CLAUDE.md` '파일 분담' 표의 중괄호를 design.md 1절과 같게.
4. 커밋·푸시한 뒤 사람이 할 일을 안내한다: (개인) Create PR → 표본을 보고 기대 결과를 불러 줌 → Merge → GitHub 웹에서 Issue 등록 / (팀) PR → 리뷰 → 병합 → 각자 Issue 등록.

### start #n — Issue 하나 시작

1. 사용자가 붙여 넣은 Issue 본문과 PRD·계획·설계 메모를 읽는다.
2. 완료 기준과 **작은 구현 순서**(2~4단계, 단계마다 무엇으로 확인할지), 사람이 화면에서 볼 것을 보여 준다. 이때는 파일을 고치지 않는다(Plan 모드로 부르면 좋다).
3. 팀 모드는 `docs/design.md` 1절의 담당 파일만 고치는 계획인지, 저장소를 3절 공통 함수로만 쓰는지 확인한다. ①의 뼈대 Issue는 `tools/pages/` 파일을 만들지 않는다(②③ 담당).
4. 사용자가 승인하면 step으로 넘어간다.

### step — 작은 단위 하나

1. 이번 단위의 성공 조건과 고칠 파일을 한 줄로 밝힌다.
2. 구현한다.
3. 확인한다: 코드 읽기·문법 확인·함수 시험, 팀은 `python tests/run_acceptance.py`. 버그를 고칠 때는 가능하면 먼저 실패하는 경우를 재현한다.
4. 실패하면 원인을 고치고 다시 확인한다. 환경 때문에 못 한 확인은 "미실행"으로 남긴다.
5. diff를 보고 무관한 변경·디버그 출력·개인정보·외부 주소가 없는지 확인한다.
6. 이번 단위 파일만 커밋한다. 메시지 = 커밋 머리 + Issue 번호 + 한 줄(예: `[M5] #3 화면 틀`, `[팀-기능A] 표본 붙여 넣기`). 세션 브랜치에 푸시한다.
7. 보고: 커밋 메시지, 확인 결과, 사람이 화면에서 볼 것(브랜치 ZIP을 받아 HTML을 열어 무엇을 해 볼지), 다음 단위. 사람이 "화면에서 이렇게 봤어"라고 알려 주면 그 부분만 고친다. 두 번 고쳐도 안 되면 직전 커밋을 되돌리는 커밋을 만들고(기록은 지우지 않음) 더 작게 나눠 제안한다.

### review — 배포 확인·자체 검토

1. 변경 전체를 PRD 성공 시나리오와 계획(팀은 `tests/acceptance.md`)에 대조한다. 확인할 것: 실패·경계 입력에서 어떻게 되는가, 입력 확인, 개인정보, 범위 밖 변경, 외부 주소·fetch·외부 라이브러리, 빠진 확인.
2. S마다(팀은 AC마다) **통과 / 실패 / 미검증**을 쓰되, 결과·근거는 **사람이 배포 주소(병합 전이면 브랜치 ZIP)에서 확인해 불러 준 것**만 적는다. 불러 주지 않았으면 미검증으로 둔다.
3. 발견 사항마다 심각도·위치·발생 조건·영향·고칠 방법을 쓴다.
4. 문서 맨 위에 **"AI 자체 검토 — 사람 리뷰 승인이 아님"**을 쓴다.
5. 개인 모드는 `checks/m5_check.md`로 저장하고 `docs/m5_plan.md` 1절 상태·4절 배포 주소, `README.md` 'M5 배포' 절을 채워 커밋한다. 팀 모드는 PR 본문에 붙일 검토 절로 보여 준다.
6. 실패한 S가 있으면 새 Issue 초안(제목 `[M5] S{번호} 실패 — {한 줄}`)을 보여 준다.

### ship — 병합 전 PR 본문

1. PR 본문 초안을 만든다: 첫 줄 `Closes #n`(팀 ①의 뼈대 PR과 1차 시험·README PR은 `Refs #n`) · 목적 · 범위(한 것/안 한 것) · 검증 결과(세션이 한 확인 + 사람이 화면에서 확인한 것) · 미실행 확인 · 위험 · 되돌리는 방법(병합 뒤 Revert).
2. 개인 모드는 AI 자체 검토(바뀐 코드에서 찾은 문제·외부 주소·실명 여부)와 **"독립 리뷰 없음(1인 프로젝트) — AI 자체 검토 + 소유자 화면 확인으로 대신함"**을 넣는다.
3. 사람이 할 일을 순서대로 안내한다: PR 본문에 붙여 넣기 → (팀) Ready for review·리뷰 짝 지정·승인 → Files changed 확인 → Merge → Issue가 닫혔는지 확인 → 1~2분 뒤 Pages 주소로 확인 → 다음 Issue.
4. 자기 PR을 승인하거나 병합하지 않는다. 승인 조건(팀: 조원 1명 승인, 리뷰 뒤 코드가 바뀌었으면 다시 승인)이 안 됐으면 병합하라고 하지 않는다.

## 5. 하지 않는 것

- PR·Issue를 직접 만들거나 병합하지 않는다(초안 글만).
- main에 푸시하지 않는다. 강제 푸시하지 않는다.
- 확인을 지우거나 기대 결과를 웹앱 결과로 바꿔 적지 않는다. 사람이 하지 않은 화면 확인을 통과로 적지 않는다.
- 실제 업무 자료·개인정보·외부 주소를 쓰지 않는다.
- Issue 완료 기준에 없는 기능을 "하는 김에" 넣지 않는다. 팀은 담당 밖 파일, `common.js`(①만)를 고치지 않는다.

## 6. 출력

| 모드 | 호출 | 파일 |
|---|---|---|
| 개인 | plan | `docs/issues_draft/m5_*.md`, `docs/m5_plan.md`, `data/m5_sample.*`, `CLAUDE.md` 5절 |
| 개인 | step | `tools/m5_*.html` |
| 개인 | review | `checks/m5_check.md`, `docs/m5_plan.md` 1·4절, `README.md` 'M5 배포' 절 |
| 팀 | plan | `docs/design.md`, `docs/team_plan.md`, `docs/issues_draft/1~4.md`, `CLAUDE.md` 파일 분담 표 |
| 팀 | step | `docs/design.md` 1절의 담당 파일, ④는 `data/team_sample.*`·`tests/acceptance.md`·`tests/run_acceptance.py` 맨 위 설정 |
| 둘 다 | ship | PR 본문 초안(채팅으로 보여 줌) |

계획·검토 파일의 칸은 레포의 양식(`docs/m5_plan.md`, `checks/m5_check.md`, `docs/team_plan.md`, `docs/design.md`, `tests/acceptance.md`)을 따른다. 양식이 있으면 칸을 채우고, 없으면 같은 칸으로 새로 만든다.

## 7. 예시

```text
/prd-build plan
/prd-build start #2
/prd-build step
/prd-build ship
/prd-build review
```

팀: `/prd-build start #4` → `/prd-build step`(반복) → `/prd-build ship`
